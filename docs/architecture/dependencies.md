# Architecture graph

HiFiScout derives its architecture diagrams and boundary checks from the same ES module import graph under `src/` and `frontend/`. The diagrams are generated by dependency-cruiser; they are not hand-maintained copies of the code structure.

## Generated overview

The overview collapses modules to folder depth 2 so subsystem relationships remain readable as the codebase grows. It is generated with dependency-cruiser's Mermaid reporter and rendered with a pinned Mermaid.js browser module.

## Enforced boundaries

Every rule in `.dependency-cruiser.json` has `error` severity, so `vp run docs:architecture:check` fails the build instead of reporting advice. These rules encode boundaries that are already load-bearing:

- **Acyclic** — first-party dependencies under `src/` and `frontend/` must stay acyclic.
- **Contract boundary** — `src/api/contracts.ts` may depend only on the catalog type vocabulary, `frontend/` may reach `src/` only through that one file, and `src/` never imports `frontend/`. The browser bundle therefore shares the HTTP contracts and nothing else.
- **Domain above storage** — `src/catalog/` must not import `src/db/`. Repositories must not take runtime dependencies on the crawler or HTTP layer; erased type-only contracts are allowed.
- **Shops stay plugins** — generic code composes shops through `src/crawler/shops/index.ts`; an adapter cannot reach persistence, search, evidence, HTTP, or the API except the activity-policy vocabulary; and catalog/repository code never imports shops.
- **Knowledge Catalog separation** — the crawler and the verification pipeline meet through the database rather than each other's types, and `src/knowledge-catalog/policy.ts` keeps I/O out of its retry, lease, and promotion decisions.
- **Product search SQL stays a vocabulary** — `src/db/product-search-entity-sql.ts` may import nothing from `src/`. Current sync/rebuild paths share the SQL vocabulary and the guarded exact-identity helpers; historical migration backfills retain their original rollout SQL. See [Data platform architecture](../data-platform-architecture.md) for both catalog and fallback grouping rules.

Each rule carries a `comment` describing the failure it prevents, and that text is what the check prints on a violation. Add new rules the same way: state the regression, not merely the restriction.

## Generation pipeline

```sh
vp run docs:architecture:check
vp run docs:architecture
```

`docs:architecture:check` validates the import graph against `.dependency-cruiser.json`.

`docs:architecture` performs three outputs from that same graph:

1. `docs/public/generated/dependencies.html` — the complete module-level dependency report.
2. `docs/public/generated/architecture.mmd` — a folder-depth-2 Mermaid flowchart suitable for GitHub/GitLab and other Mermaid-aware tooling.
3. `docs/public/generated/architecture.html` — a browser-rendered view of that Mermaid source for the VitePress site.

dependency-cruiser parses the TypeScript sources with its own pinned `typescript@6.0.2`, supplied through the `vp dlx --package` invocation in the `docs:architecture*` scripts. dependency-cruiser 18.1.0 does not yet accept the project's TypeScript 7 compiler, and without a compatible parser it can cruise zero modules rather than providing a useful graph.

The generated HTML loads a pinned Mermaid.js version only in the documentation browser page. Mermaid is not a Worker runtime dependency and does not enter the production bundle.

## Source of truth

Do not manually edit the generated diagrams. Change imports or architecture rules, then regenerate. This keeps architectural documentation mechanically aligned with the code instead of requiring a second hand-maintained model.
